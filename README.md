##Exploring and Testing APIs with Postman
#1. API Choice and Base URL
For this assignment I used JSONPlaceholder, a free fake REST API used for testing and prototyping. It supports full CRUD (Create, Read, Update, Delete) operations on resources such as posts, users, and comments, which made it ideal for practicing API testing in Postman without needing a real backend.

Base URL: https://jsonplaceholder.typicode.com
Resource used for CRUD demonstration: /posts
2. Authentication Method Used
JSONPlaceholder is a public, unauthenticated API — it does not require login credentials or tokens to access its endpoints. To demonstrate an understanding of authentication mechanisms in Postman regardless, I configured a Bearer Token authorization on one of my requests, showing how a real token-protected API would be accessed.

In a real authenticated API, this token would be generated by first sending a login request, capturing the returned token, and storing it in an environment variable (e.g. {{auth_token}}) so it can be reused automatically across requests via a pre-request script.

All requests reference this variable instead of hardcoding the URL, e.g. {{base_url}}/posts/1. This means if the API's base address ever changed, it only needs to be updated in one place rather than in every saved request.

5. Automation and Testing
I added a Postman test script to the "After response" section of the Scripts tab on one of my requests:

pm.test("Status code is 200", function () {

    pm.response.to.have.status(200);

});

This automatically checks, after every send, that the request succeeded  shown as a pass/fail result under the Test Results tab. This test passed successfully.

(Insert screenshot: Test Results tab showing a passed test)
6. Collection Runner
All requests (GET, POST, PUT, DELETE) were saved into a single Postman Collection named CRUD Collection. Using the Collection Runner, all saved requests were executed in sequence, confirming each one returns the expected status code and, where applicable, passes its test script.

7. Summary
This assignment demonstrated the full lifecycle of interacting with a REST API through Postman: exploring endpoints, performing all four CRUD operations, configuring authentication, using environment variables to avoid repetition, and automating verification with test scripts and the Collection Runner. Working through each operation individually  rather than just reading about them  made clear how the HTTP method and the presence/absence of a resource ID in the URL together determine what action is performed on an API resource.
